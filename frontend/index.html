Azure Managed Identity

In order to Read/Write to Cosmos DB, you need to set up the Managed Identity (MI) to have both Control Plane and Data Plane access.

Control Plane Access

Control Plane access is pretty simple. Azure already gives you the option to assign the necessary role directly:

  • Cosmos DB Account Reader Role

Data Plane Access

However, in order to actually read/write data into a collection in Cosmos DB, you need Data Plane access in the form of:

  • Cosmos DB Built-in Data Reader
  • Cosmos DB Built-in Data Contributor

These roles are not available in the Azure Portal. You need to use Azure CLI or PowerShell to assign them.

The command is:

az cosmosdb sql role assignment create \
                                --account-name {Cosmos DB Account Name} \
                                --resource-group {Resource Group Name that has the Cosmos DB account} \
                                --role-definition-id {role id number} \
                                --scope "/dbs/{collection name}" \
                                --principal-id {MI Client Id that you want to assign the role to}

Built-in role IDs:

  • Cosmos DB Built-in Data Reader: 00000000-0000-0000-0000-000000000001
  • Cosmos DB Built-in Data Contributor: 00000000-0000-0000-0000-000000000002

Related: CI/CD with GitHub Actions

In order to do CI/CD with GitHub Actions, you also need to assign the MI access to the storage account that you are using to host the static website. Luckily, this is easier to do, since Azure already has the built-in role Storage Blob Data Contributor — you can assign this role to the MI directly in the Azure Portal. See below for more details.

Patch vs Read & Write:

For this project, I used the Patch method to update a document in Cosmos DB rather than reading and then writing. This was done to avoid race conditions where two users are trying to update the same document at the same time. Using Patch, the document is updated in one atomic operation, which avoids the race condition.

CI / CD with Github Actions:

In order to do CI/CD with Github Actions, you need to set up a Service Principal in Azure and give it the necessary permissions to deploy to your Azure resources.

App Registration & Federated Credential

Created a Microsoft Entra ID App registration, then created a Federated Credential for the App registration with the following settings:

Federated Credential Scenario: GitHub Actions deploying Azure resources

  • Organization: {your github username}
  • Organization ID: {your github organization id} — this can be found by going to https://api.github.com/users/{your github username} and taking the value of the "id" field
  • Repository: {your github repo name}
  • Repository ID: {your github repo id} — this can be found by going to https://api.github.com/repos/{your github username}/{your github repo name} and taking the value of the "id" field
  • Entity Type: Branch
  • Based on selection: main
  • Issuer: https://token.actions.githubusercontent.com (default)
  • Subject: repo:{your github username}/{your github repo name}:ref:refs/heads/{your branch name}
  • Audience: api://AzureADTokenExchange (default)

RBAC Permissions

In order for the CI/CD to work, you need to give the App registration the necessary RBAC permissions to deploy files to the Storage Account for static web hosting.

  • Assigned the App registration the built-in role Storage Blob Data Contributor on the Storage Account that is hosting the static website.

GitHub Actions Workflow

For CI/CD from GitHub Actions, you need to set up a workflow file in GitHub. You can find the YAML in the GitHub repo, but essentially, the workflow file does the following:

  • On push to the main branch, it will run the workflow.
  • It will use the Azure/login action to log in to Azure using the App registration and Federated Credential that was set up earlier.
  • I stored the Azure Client ID (App Registration's ID), Azure Tenant ID, and Azure Subscription ID in GitHub Secrets, and then used those secrets in the workflow file to log in to Azure.
  • It will then use the Azure/CLI action to run the az storage blob upload-batch command to upload all files in the dist folder to the Storage Account for static web hosting.
  • It will purge the CDN cache for the Storage Account to ensure that the latest files are served to users.
